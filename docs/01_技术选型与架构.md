# 01 技术选型与架构

状态：已与项目负责人确认的选型（2026-10-24）。未确认项集中在 §11。

最近更新：2026-10-24，已按 P2b 实现同步。

## 1. 范围

- 本服务跑在算力盒（图为 TW-T201P / Jetson Orin Nano 8G）上，是整机的"大脑"：采集、识别、决策、对下位机发令、对 HMI 提供接口、管理样本与模型。
- 阶段一目标：**验证识别准确率**（采集 → 切图 → 人工标定 → 训练 → 跨批次评估），喷阀与下位机先用模拟实现。
- 不包括：HMI 界面（其他同事）、下位机固件、机械气路。

## 2. 已拍板的选型

| 选型项 | 决定 | 备注 |
|---|---|---|
| 运行环境 | JetPack 6.x（L4T r36、Ubuntu 22.04、Python 3.10、CUDA 12、TensorRT 8.6/10.x 视小版本）；Orin Nano **8G** | 版本以 `cat /etc/nv_tegra_release` 为准 |
| 语言 | **Python 为主**；热点路径（采集/分割）测出瓶颈再以 C++ 扩展（pybind11）或独立进程替换 | 一路相机 9 kHz 行频 ≈ 110 MB/s，按 512 行分块 ≈ 17.6 块/s，Python + OpenCV 可承受 |
| 相机接入 | 海康 **MVS SDK（Linux aarch64）** 官方 Python 封装；抽象 `Camera` 接口 + Mock | 备选 Aravis |
| 采集方式 | RGB8；采样/标定用整帧（高 4096），**运行时按 256~512 行分块流水**；生产用**编码器行触发**，阶段一可内触发固定行频 | 行频不够时切 Bayer8（28 kHz）+ GPU 解拜耳 |
| 分割切图 | OpenCV 经典法（逐列背景模型 → 颜色距离阈值 → 开闭运算 → 连通域 → 带 mask 裁切），粘连可选分水岭 | 参数即 HMI"采集设置" |

| 推理 | ONNX → **TensorRT FP16** 引擎（算力盒现场生成）；PyTorch FP16 兜底 | TensorRT Python API，用 torch 张量做显存缓冲，不引入 pycuda |
| 训练执行 | 独立子进程（`multiprocessing` spawn），低优先级；结束后若该模型为当前方案则自动重新部署 | 训练崩溃不影响主服务 |
| 进程/线程 | 单主服务进程（systemd）：asyncio API + 流水线线程（采集 / 处理 / 下位机发送）+ 训练子进程 | GIL 争用超标再拆进程 + 共享内存 |
| HMI 接口 | **HTTP REST + WebSocket（FastAPI）**，JSON；缩略图/图片走静态 URL；OpenAPI 自动文档作为契约 | 端口默认 8000 |
| 下位机链路 | **以太网 TCP 长连接**（下位机作 server，后端重连），TCP_NODELAY + keepalive + 应用层心跳；二进制帧 + 序列号 + CRC16 | 备选 CAN；UART 仅应急 |
| 喷阀时序分工 | 后端给出"喷头区间 + 颗粒经过相机的行号"，**下位机按编码器计数换算开阀时刻**；延时/开阀/维持/重吹参数在下位机执行 | Linux 非实时，不自己计时 |
| 模型/类别数 | **可配置**（默认 7 个模型、类别 A~G） | HMI 按配置渲染 |
| 数据存储 | NVMe 上文件系统目录 + JSON 元数据；配置 JSON + pydantic 校验 | 样本上十万再加 SQLite 索引 |
| 开发/测试 | Mock 相机（回放图片目录）+ Mock 下位机；pytest；整套可在 Mac/PC 跑 | Claude Code 无硬件可开发自测 |
| 部署 | venv + 锁定版本 requirements + systemd（Restart=always）+ journald | 不用 Docker |

## 3. 网络拓扑

```
                 ┌──────────────────────────── 算力盒 TW-T201P ────────────────────────────┐
 海康线阵相机 ───┤ eth(5G)  192.168.10.1/24  ←直连，MTU 9000，静态 IP，相机 192.168.10.10   │
                 │                                                                         │
 工业交换机 ─────┤ eth(1G)  192.168.1.10/24                                                │
   ├── HMI 工控机 192.168.1.20   ←→  HTTP :8000 / WebSocket                                 │
   └── 下位机主控 192.168.1.30   ←→  TCP :5000（下位机 server）                               │
                 └─────────────────────────────────────────────────────────────────────────┘
```

- 相机独占一个网口：满行频 ≈ 885 Mbps，和别的流量共口必丢包；5G 口有裕量，后续多相机可在 5G 口下挂交换机。
- 全部静态 IP，写在 `config/*.yaml`；Type-C 口的 192.168.55.1 是刷机口，不用。
- 系统调优：`ip link set <eth> mtu 9000`、`sysctl net.core.rmem_max=26214400 net.core.rmem_default=26214400`、`nvpmodel -m 0`、`jetson_clocks`；SDK 侧开启 GVSP 丢包重传、合适的 `GevSCPSPacketSize`（巨帧下 8164）与较大的图像缓存节点数。

### 4.2 运行时数据流（分选模式）

```
相机 SDK 回调（512 行 × 4096 × RGB）
  → 环形队列（丢块计数）
  → 处理线程：
      拼接上一块尾部 overlap 行 → 逐列背景差分 → 阈值 → 开/闭运算 → 连通域
      → 跨块去重规则（见 §5.2）→ 每颗矿石：bbox、质心 x、尾沿行号、面积、带 mask 的小图
      → 统一预处理（去背景、补方、缩放、归一化）→ 批量推理（TensorRT）→ 概率
      → 决策（runtime/decision.py）：未截断 且 类别 ∈ 吹气类别集合 且 conf ≥ min_confidence/255 且 size_norm ∈ [size_min, size_max] → 吹
      → 喷头映射：颗粒 x 区间（+offset_x）→ 喷头编号区间（§5.4）
  → 下位机发送线程：EJECT 帧（行号 + 喷头区间）合并为每块一帧批量发送
  → 统计：每类计数、吹气计数、块处理耗时、丢块数 → WS 每秒推送
```

吹气决策口径（`decision.decide`，docs/01 §9 blow 分组）：取 top-1 类别 `cls` 与置信度 `conf`；**吹气当且仅当**（1）颗粒未被截断（`truncated` 的半颗矿石颜色 / 粒度都不可信，默认不吹，`blow_truncated=True` 可放开）；（2）`cls ∈ blow.classes`；（3）`conf ≥ blow.min_confidence / 255`；（4）`size_norm = round(255 · sqrt(min(area, max_area_px) / max_area_px))` 落在 `[blow.size_min, blow.size_max]`，`max_area_px` 取 `capture.max_area_px`——用面积平方根（≈ 等效直径）而不是面积本身归一化，使 0~255 的粒度滑块与颗粒线尺度近似线性。不吹的 `reason ∈ class_not_selected / low_confidence / size_out_of_range / truncated / no_classifier`（未部署分类器或推理失败的块按 `no_classifier` 处理）。决定吹但颗粒完全落在 `[start_px, end_px)` 之外、映射不到喷头的计入 `eject_skipped`。**滑块的确切含义与截断颗粒是否吹待客户确认**（§11 #5 / #11）。

采样模式与分选模式共用采集与分割，只是分割出的小图进样本库而不进分类器（被截断的颗粒也不进样本库）。

### 4.3 状态机

```
 boot → init(打开相机、连接下位机、加载当前部署模型；单个设备失败只置故障不抛)
   ├─ 有故障 → fault（开机时 TCP 下位机尚未连上会先短暂 fault）
   ├─ 无故障 且 auto_run_on_boot 且前置条件满足 → running
   └─ 否则 → stopped（faults 列表说明原因）；auto_run_on_boot 在启动后 60 s 窗口内每秒重试 start

 stopped ──start──► running ──pause──► paused ──start──► running
    ▲                 │                   │
    └──────stop───────┴────────stop───────┘
 stopped/paused ──capture job──► sampling ──job 结束──► 回到原状态
 sampling ──stop──► stopped（取消采样任务）
 任意状态 ──任何故障置位（相机掉线/超时、下位机断线/事件/故障位、流水线/分类器连续失败、模型加载失败）──► fault
          （自动下发 STOP、停流水线、取消采样/喷阀检测任务；全部故障清除后回到 stopped，需人工 start）
 fault ──stop──► fault（幂等：不清故障，但后端仍向下位机下发 STOP）
 fault ──fault_cleared──► stopped
```

- `running`：给料 + 输送 + 喷阀使能，识别并下发喷阀；`paused`：PAUSE 已下发（停给料、不喷，输送是否停由下位机策略决定，TBD），后端流水线**继续采集 / 分类 / 统计但不吹**（`set_blow_enabled(False)`），恢复 `running` 只发 RUN、**不重新 SYNC 也不重置行号**（假定下位机 PAUSE 时输送带停、编码器计数与行号同步冻结；若下位机 PAUSE 时输送带继续走则需恢复时重新 SYNC——TBD，§11 #10）；`stopped`：全停。
- 采样（sampling）要求当前为 stopped/paused，且独占相机：来源为 paused 时挂起分选流水线，采样结束恢复为不吹的分选流水线并回到 paused（不重置行号）；训练（train job）可在任意状态发起，在子进程中以低优先级执行。
- 故障（`fault`）：任何故障置位即进入 fault，后端另起线程取消进行中的采样 / 喷阀检测任务、尽力下发 STOP（下位机断线故障且无流水线在跑时不发）、停流水线；故障抖动（置位后立刻清除、操作员已重新 start）时迟到的反应线程复查状态后不再动作。全部故障清除后 `fault_cleared` 回到 `stopped`，需人工 start。故障码：`CAMERA_{id}_DISCONNECTED`（打开失败 / 掉线 / 开流失败）、`CAMERA_{id}_TIMEOUT`（运行中 `pipeline.frame_timeout_s` 无帧而相机仍在线；流水线再收到帧、或流水线已停且相机在线时由设备巡检清除，操作员 `stop` 也清除）、`MCU_DISCONNECTED`（断线 / 心跳或 ACK 超时）、`MCU_EVENT_{code:04X}`（下位机 level=2 事件，重连后清除）、`MCU_FAULT_{code:04X}`（STATUS 故障位，位清除即清除；目前只有 Mock 链路产生）、`PIPELINE_ERROR`（连续 20 块处理失败或采样后恢复流水线失败；操作员 `stop` 确认后清除）、`CLASSIFIER_ERROR`（分类器连续 20 块推理失败；粘性，重新部署清除）、`MODEL_LOAD_FAILED`（开机加载部署模型失败；重新部署清除）。
- 开机自动运行：`auto_run_on_boot=true` 时启动后 60 s 窗口内每秒重试 start（前置条件：已部署模型、相机与下位机均连接）；开机时 TCP 下位机尚未连上会先短暂 `fault`，窗口内**保留**重试，故障清除回到 stopped 后下一拍自动运行；只有被人工操作带入 running / paused / sampling 才放弃，超时放弃并记日志。
- `fault` 态下 `stop` **允许且幂等**：状态仍为 `fault`、不清故障（不是 409），但后端仍向下位机下发 STOP（全停的安全语义，HMI 的停止按钮在故障态不置灰）；`fault_cleared` 后回到 `stopped`，需人工再次 `start`。`sampling` 态下 `stop` 允许，调用方取消采样任务后回到 `stopped`。其余幂等事件（running+start、paused+pause、stopped+stop）不报错、不触发监听；非法迁移返回 409 `CONFLICT`，`detail.reasons` 见 docs/03 §4。

## 5. 识别管线设计

### 5.1 采集
- `Camera` 接口：`open/close`、`get/set_params`（曝光、白平衡模式、宽、高、OffsetX、行频、触发源）、`start_stream(chunk_lines)`、`frames()` 迭代器（产出 `Frame(seq, line_start, image[h,w,3], timestamp)`）、`snapshot(height)`、`awb_once()`。
- 行号 `line_start` 是自 `SYNC` 以来的累计行计数（块序号 × 块高，SDK 丢块时按丢失块数补偿），是后端与下位机的共同时间轴（§5.5）。
- 白平衡策略：对白板/灰板做"一次"白平衡后**锁定**，禁止连续自动白平衡（会随矿石配比漂移，破坏颜色特征）。曝光同样固定。
- 行触发：编码器 → 相机 Line 输入 → 相机内分频/倍频得到行触发，保证每行对应固定皮带位移；阶段一无编码器时用内触发固定行频并记录带速。

### 5.2 分块与跨块去重
- 处理图 = 上一块**处理图**尾部 `overlap_used` 行 + 当前块（`pipeline.overlap_lines`，应 ≥ 最大矿石长度的行数，默认 256）。
  - 尾部缓存取自上一块处理图（而非当前块）的最后 `min(overlap, 处理图高)` 行。块高 < overlap（合法配置，如 `runtime_chunk_lines=128` / `overlap_lines=256`）时，`overlap_used = min(overlap, 自上次断块起的累计行数)` 在起始/断块后逐块增长，到达 overlap 后稳定，因此长度 ≤ overlap 的矿石不会因块高不足被截断。
  - 处理图第 0 行的全局行号 `y_offset = line_start − overlap_used`，颗粒 `trailing_line = y_offset + trailing_y`（§5.5 的下位机时间轴）。
  - `seq` 不连续（丢块/回退）、`line_start` 与上一块 `line_end` 不接、图像宽度变化 → 放弃尾部（`overlap_used = 0`）并计 `resets`；丢块按 seq 差计入 `dropped`。
- 只处理满足 `max_y ≥ overlap_used − 1` 且 **不触及处理图底边** 的连通域：
  - `max_y < overlap_used − 1` 的对象在上一块已完整处理过（计 `skipped_seen`）；
  - 触底的对象留到下一块（计 `deferred`，那时它会完整出现在重叠区内）；其 x 区间与全局顶行被记录，供下一块判定截断；
  - 顶到处理图顶边且 `overlap_used > 0` 的对象，用**上一块延后颗粒中 x 区间与之重叠者**精确判定：任一从 `y_offset` 之前开始 → `truncated=True`、记 warning 并按截断处理（尾沿行号仍正确）；全部从 `y_offset`（含）之后开始 → 恰好完整可见，不算截断。上一块只 `push` 未 `select`（无延后信息）或延后颗粒中找不到 x 区间重叠者（分割结果不一致）时，退回"顶到顶边即截断"的启发式（高度恰为 `overlap_used` 的完整颗粒会误报）；断块后的首块 `overlap_used = 0`，**不做截断判定**，此时超长颗粒可能以未标记截断的形式出现（即下文 `lost` 为"上界"的原因）。
- `stats()`：`frames / dropped / resets / deferred / skipped_seen / truncated / selected / lost`。`lost` = 断块时上一块已延后、因此再也无法被完整处理的颗粒数（上界：其中特别长的可能在断块后首块以未标记截断的形式出现）。
- 单元测试：构造跨两块的合成颗粒，验证恰好处理一次；块高 < overlap、丢块重同步、截断精确判定各有用例。

### 5.3 分割（采集设置参数）
| 参数 | 含义 | 默认 |
|---|---|---|
| `bg_mode` | `column`（空皮带逐列背景，线阵推荐）/ `color`（固定背景色） | column |
| `bg_color` | `color` 模式的背景 RGB | [0, 0, 255] |
| `bg_threshold` | 与背景的颜色距离阈值：OpenCV 8 位 Lab 约定（L∈[0,255]，a/b 偏移 128）下的欧氏距离，0~255 | 40 |
| `erode_px` / `dilate_px` | **先腐蚀再膨胀**（顺序执行，椭圆核，各 0~50）：腐蚀去噪、膨胀填洞/连接；默认 1/2 使 mask 净外扩 1 px | 1 / 2 |
| `min_area_px` / `max_area_px` | 连通域面积过滤；`min` 在拆粘连**之前**应用（太小的不值得拆），`max` 在拆分**之后**对每个碎片应用（几颗合格矿石粘成一团可能超限） | 400 / 2 000 000 |
| `margin_px` | 裁切外扩（bbox 本身不含 margin；越界部分 RGB 填背景色、alpha=0） | 8 |
| `split_touching` | 拆粘连：距离变换 → 局部极大作种子 → 鞍点水位判独立峰 → 其余像素按最近种子归属（**不是** `cv2.watershed`）；内切圆面积 > `max_area_px` 的实心大块（皮带边条、整帧前景）不拆 | false |
| `bg_learn_frames` | 学习背景用的空皮带帧数 | 20 |
| `bg_adapt_rate` | 运行时逐列背景缓慢自适应的 EMA 速率，只更新本帧**完全无前景**的列；0 = 关闭；**仅 `bg_mode=column` 有效**（`color` 模式无学习/自适应/持久化） | 0（0~0.1） |

输出 `Particle(bbox, centroid_x, centroid_y, area, trailing_y, crop_rgba, touches_top, touches_bottom, truncated, trailing_line, extra)`（vision / runtime / data / api 共用契约，字段只增不删），`crop_rgba` 的 alpha 即 mask，列表按 `trailing_y` 升序。背景模型随"学习背景"操作更新并持久化到 `background/cam{id}.npz`，`bg_adapt_rate > 0` 时按上表缓慢自适应（只在无颗粒的列上更新；`color` 模式忽略该项）。

### 5.4 像素 → 喷头映射
- 输入：起始像素 A、结束像素 B、喷头数 N（默认 64）。`(B−A) = N·q + r`，前 ⌈r/2⌉ 个与后 ⌊r/2⌋ 个喷头各 q+1 像素，其余 q 像素（原始需求 §3）。
- 提供 `pixel_to_nozzle(x)`、`ranges()`（第 1..N 号喷头的像素闭区间）、`span(x0, x1, expand)` / `global_span`、给 HMI 的映射表 `to_dict()`；颗粒宽度跨多个喷头时输出 `[nozzle_first, nozzle_last]` 区间（向两侧各扩 `pipeline.nozzle_expand` 个后裁到 1..N）。`span` 的 `x0 > x1` **自动交换**两端（视作同一闭区间），与有效区 `[start_px, end_px)` 完全不相交返回 None，部分相交只取相交部分。
- **x 一律是传感器坐标**：`start_px/end_px` 按整幅传感器（0~4096）定义，而 `Frame.image` 只是宽 `width` 的 ROI，`传感器 x = 图像列号 + CameraConfig.offset_x`，流水线在查表前必须先加 `offset_x`。
- 多相机时喷头全局编号 = `(camera_index) × N + 本地编号`，对应 HMI 的"孔位 0~768"。

### 5.5 时序模型
- 相机行触发与下位机编码器计数来自**同一编码器**：行号 ⇔ 皮带位移。`SYNC`（下位机编码器清零）+ 全部相机 `reset_line_counter()` **只在点击运行（`RuntimeService.start()` 的 stopped → running 路径）一处同时完成**，随后启动流水线并发 RUN；paused → running、采样结束恢复分选流水线、下位机重连等场合**都不**再 SYNC 或重置行号（`Pipeline.start(reset_lines=False)` 缺省），保证 `EjectItem.line` 与编码器同一零点；两者零点误差由"延时"参数标定吸收。
- 后端对每颗矿石上报 `trailing_line`（尾沿行号）与喷头区间；下位机在 `encoder_count == trailing_line + delay` 时开阀，开阀时间/维持/重吹由下位机执行。
- 后端处理延迟只需小于"相机到喷阀的皮带行程时间"即可，不影响开阀精度。目标：512 行块端到端（块到达 → EJECT 发出）p99 < 80 ms。
- 无编码器（阶段一内触发）时行号按固定行频换算为时间，仅用于验证，不用于生产。

### 5.6 预处理（训练/推理共用）
1. RGBA 小图 → 背景像素置为常数（黑）；
2. 按长边补成正方形（常数填充）；
3. 缩放到 `image_size`（默认 160，可选 128/224）；
4. RGB、[0,1]、ImageNet 均值方差归一化；
5. 输出 `float16/32 CHW`。训练时的增广只在此函数之前做几何变换，颜色增广仅限小幅亮度/对比度（±10%），**禁止色相/饱和度抖动**（颜色是主要判据）。

## 6. CNN 训练与部署

### 6.1 模型
- 默认 `resnet18`（ImageNet 预训练，替换 fc → 类别数）；可选 `mobilenet_v3_large`。
- 预训练权重文件随仓库离线放在 `oresorter/ml/weights/`（`resnet18-f37072fd.pth`、`mobilenet_v3_large-8738ca79.pth`，来自 torchvision 发布），运行时不下载。

### 6.2 一键训练配方（固定，不暴露超参给操作工）
- 数据：当前模型目录下所选类别的全部有效样本（排除软删除）；每类 < `min_samples_per_class`（默认 20）拒绝训练并返回原因；分层划分 80/20 作验证集（可选 5 折交叉验证模式用于评估报告）。
- 采样：类别均衡采样（WeightedRandomSampler）。
- 增广：水平/垂直翻转、随机 90° 旋转、随机缩放 0.8~1.2、亮度/对比度 ±10%。缩放实现为**保持画幅**的缩放（缩小则居中补零，放大则中心裁切，放大倍率另受"前景外接框不出画布"的上限约束），否则预处理的补方+缩放会把整体缩放抵消；颜色变换只作用于 alpha>0 的像素，不改色相/饱和度。
- 优化：AdamW；先 3 个 epoch 只训分类头（lr 1e-3），再全网微调（lr 1e-4，cosine 衰减）；label smoothing 0.05；batch 32；AMP FP16；最多 30 epoch，验证 macro-F1 连续 5 轮不升则早停；总时长上限 `max_train_minutes`（默认 10）。
- 输出：`best.pt`、`model.onnx`（动态 batch，opset 17）、`metrics.json`（验证准确率、macro-F1、混淆矩阵、每类 P/R/F1/support、训练曲线、`artifacts`）、`train.log`、`meta.json` **合并**更新（read → merge → 原子写：`trained_at`、`algo`、`image_size`、`classes`、`metrics_summary`；`sample_counts` 按类别合并而非整体替换，只训 A/B 不抹掉 C~G 的计数；`version + 1`）。
  - 产物一致性：写新 `best.pt` 之前先删除上一轮遗留的 `model.onnx` / `model.plan` / `model.json`，`train/` 下任何时刻不会混有两次训练的产物；ONNX 导出失败不算训练失败，只记 warning，并在 `metrics.json` 与返回值的 `artifacts` 中标明 `{"onnx": false, "onnx_error": "..."}`。
  - 入口：`train.run(model_dir, classes, cfg, *, class_names, progress_cb, stop_event)`；子进程 `python -m oresorter.ml.train --model-dir D --config YAML [--classes A,B] [--nice 10]`，其 `--image-size` 只接受 128/160/224（`--allow-any-image-size` 仅测试用）；`cli eval --image-size` 只做评估、不产出可部署模型，**当前实现**接受 ≥ 8 的任意值——与 §9 `ml.image_size ∈ 128/160/224` 不一致，是否同样收紧待拍板（§11 #9），未拍板前不要把 ≥ 8 当作规范。
- 预期耗时：1000 张样本、160 px、ResNet18，在 Orin Nano 8G 上约 2~4 分钟。

### 6.3 部署
- `deploy(model_id)`：用 `export.engine_matches(plan, onnx, trtexec=…, image_size=S)` 判断是否需要重建——引擎旁的元信息 `model.json` 记录 `trt_version`、`onnx_sha256`、`image_size`，任一与当前不符（或缺元信息、本机查不到 TensorRT 版本）即重建；重建用 `trtexec --onnx --fp16 --minShapes=input:1x3xSxS --optShapes=input:32x3xSxS --maxShapes=input:128x3xSxS` 生成 `model.plan`（约 30~90 s，超时 `ml.engine_build_timeout_s`，产物原子写），然后原子切换推理器；生成失败或 TensorRT 不可用时按 `prefer=("trt","onnx","torch")` 降级并上报 warning。加载引擎时核对输入尺寸与**输出类别维 == len(classes)**，不一致拒绝加载（避免越界写显存）。
- 一致性测试：同一批小图 PyTorch 与 TensorRT 输出 top-1 一致、概率误差 < 1e-2。
- 自动重新部署：训练完成时，若该模型是当前方案则自动部署（原始需求要求），切换瞬间最多影响 1 个块。

### 6.4 GPU 共享
- 训练子进程由任务层以 `--nice 10` 启动（子进程内 `os.nice`，非 POSIX/失败只告警），batch 32，AMP；分选运行中允许训练，但 HMI 应提示吞吐可能下降；推理延迟超过阈值时记录 warning。
- 显存预算：推理引擎 ≈ 200 MB，训练 ≈ 2~3 GB，相机缓冲 ≈ 100 MB，总 8 GB 共享内存足够。

## 7. 可靠性设计（工业级）

### 7.1 HMI 链路（HTTP + WebSocket）
- 后端是**状态唯一来源**；HMI 启动/重连后调用 `GET /state` 全量同步，不在前端缓存业务状态。
- 所有写操作同步返回结果（生效值、下位机确认情况、警告）；参数先校验、再持久化、再下发下位机；下位机未确认时返回 `mcu_ack=false` 并在 WS 推送最终结果。
- 写操作可带 `request_id` 幂等（纯 ASGI 中间件，只拦截 `/api/v1` 下的 POST/PUT/PATCH/DELETE：60 s 内重复提交直接回放首次完整响应并带 `X-Idempotent-Replay: 1`，错误响应同样缓存，同键并发合并等待 ≤ 30 s），防止网络重试导致重复执行。
- WebSocket：服务端每 5 s 发应用层 `ping`，客户端回应用层 `pong`，15 s 无任何客户端消息以 1001 断开；连接后首条 `state` 之后比它更旧的全量型事件（state / stats / mcu）丢弃，HMI 不会被回退到旧状态；前端断线自动重连；预览帧限频（`system.preview_max_fps`，默认 ≤ 10 fps，JPEG 质量可调），每个时隙只发最新一帧而不是堆积；预览查询参数越界一律拒绝（1008）不夹断。
- HMI 默认与后端**同源**部署（直接访问算力盒 `IP:8000`，或由 `/static` 托管 HMI 静态文件），不需要 CORS；跨源部署时在 `system.cors_origins` 列出来源，非空才挂 `CORSMiddleware`（允许全部方法与头，暴露 `X-Idempotent-Replay`）。
- `/static` 挂到数据目录，但只放行四类路径：`models/{id}/thumbs/**`、`models/{id}/samples/**`、`snapshots/*`、`previews/*`（docs/03 §12 的契约）；其余（`config.json` / `state.json` / `models/{id}/train/*` / `background/*.npz` / `logs/`）一律 404，不是契约的一部分。
- 接口带版本前缀 `/api/v1`；OpenAPI 文档由 CI 导出到 `docs/openapi.json`，前端按此联调。
- 不做鉴权（内网专用），但只监听配置的网口 IP。

### 7.2 下位机链路（TCP）
- 长连接，`TCP_NODELAY`，内核 keepalive；应用层心跳 200 ms，为"**发出即忘 + 看门狗**"：心跳不等 ACK、不重发、不计入 `ack_timeouts`（下一拍自然补上）；任何 CRC 正确的 STATUS(0x81) 帧（含只有 result 字节的 NACK）都刷新看门狗，距上次收到 STATUS 超过 1 s → `fault(MCU_HEARTBEAT_TIMEOUT)`、断开重连并进入 `fault` 状态告警；心跳被 NACK 时链路保持连接，`status.faults` 含"心跳被拒绝"。下位机侧 1 s 无心跳 → 自行停阀（安全态，需固件实现）。
- 每帧带序列号与 CRC16；控制/参数类指令必须 ACK，超时 200 ms 重发**同一 SEQ**（下位机按 SEQ 幂等），3 次失败 → `ack_timeouts += 1`、`fault(MCU_ACK_TIMEOUT)`、断开重连并抛 `McuTimeout`；EJECT 流不等 ACK（每帧 ≤ 100 条，未连接时计 `eject_dropped_offline`），但下位机每秒上报收到/执行/丢弃计数用于对账。
- 断线指数退避重连（0.5 s 起翻倍，上限 5 s）：连接失败按上述退避；"连上但不稳定"（从未收到 STATUS，或存活 < 2×心跳超时即被判故障）的连接断开后沿用并翻倍退避，只有稳定连接断开才从 0.5 s 重新开始，避免"连上→不应答→断开"的重连风暴刷屏 HMI。重连成功后全量 `SET_PARAM` + `RESET_LINK`（**不发 SYNC**，与 docs/04 §8 一致），状态机置 `stopped`，需人工再次运行；`SYNC` 只在点击运行时发送。
- 协议编解码与链路状态机在无网络情况下用 Mock 下位机（进程内 `MockMcuLink` 与协议级 TCP `MockMcuServer`）全覆盖测试。

### 7.3 相机链路
- SDK 异常、超时、丢块全部计数并上报；掉线自动重连（退避），重连后恢复参数并重新开始流；连续 N 次失败置 fault。
- 采集线程最高优先级；处理线程落后时环形队列丢最旧块并计数（不允许无限堆积）。

### 7.4 系统级
- systemd `Restart=always` + `WatchdogSec`（sd_notify）；开机自启；日志 journald（可选落盘轮转）。喂狗判定（`cli serve` → `Pipeline.healthy()`）：没有流水线在跑视为健康；运行中要求流水线线程都活着，且不出现"收到块却超过 `max(2 × frame_timeout_s, 5)` s 未处理"（处理线程卡死）才喂狗；相机静默 / 断线属于设备问题（由重连与故障表反映），**不**触发停止喂狗与重启；健康检查抛异常按不健康。喂狗间隔取 `WATCHDOG_USEC/2`（`WatchdogSec=30` → 15 s，下限 0.5 s）。`cli serve` 的 `_healthy` 遍历 `ctx.pipelines` 全部流水线，任一不健康即停止喂狗。
- 配置/元数据原子写；模型部署原子切换；磁盘剩余空间 < 阈值时拒绝采样并告警；样本数/模型目录大小有上限。
- 所有后台任务有超时与取消；主循环异常不致命（捕获、计数、告警），崩溃由 systemd 拉起。
- 48 小时连续运行无内存增长（验收项）。

## 10. 运行环境与依赖

- JetPack 6.x 自带 CUDA、cuDNN、TensorRT、`python3-libnvinfer`；`trtexec` 在 `/usr/src/tensorrt/bin/`。
- PyTorch / torchvision：必须用 NVIDIA 为 JetPack 编译的 wheel（`https://developer.download.nvidia.com/compute/redist/jp/`，按 JetPack 小版本选目录；或 Jetson AI Lab 的 pip 索引），torchvision 版本须与 torch 匹配；下载后放入内网制品库，`requirements-jetson.txt` 指向本地 wheel。
- 海康 MVS SDK：`MVS_STD_GML_V2.x_aarch64.deb`（海康机器人官网），安装到 `/opt/MVS`；Python 封装 `MvImport` 以 vendor 方式复制进 `oresorter/camera/hik_sdk/` 或通过 `PYTHONPATH` 引入。
- 其余：numpy、opencv-python-headless、fastapi、uvicorn[standard]、pydantic v2、pyyaml、pillow、onnx、scikit-learn（仅评估指标）、pytest、httpx。
- 开发机（Mac/PC）：同一份代码，不装 MVS SDK 与 TensorRT，自动降级为 Mock 相机 + PyTorch 推理。
